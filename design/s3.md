# S3 - the operation entry point

`S3` is the public entry point for the `aws s3`-style operations
(`cp` / `ls` / `mv` / `rm` / `mb` / `rb` / `presign` / `sync` / `website`). It is
a **stateless orchestrator**: it carries optional defaults for building clients
and transfers but holds no connection, so it needs no cleanup. Each method's
`Location` arguments are resolved to a `Storage` (an `S3Storage` or a
`LocalStorage`); the building blocks it drives are documented in
[`transfer.md`](./transfer.md), [`sync.md`](./sync.md), and
[`deleter.md`](./deleter.md).

Two methods - `client()` and `resolve()` - are the **customization seams**:
subclass `S3` and override them to change how clients are built or how URLs are
interpreted. SDK import timing during construction or normal operation is not
part of this interface; the only import guarantees are documented in
[`imports.md`](./imports.md).

## 1. API

```python
import boto3
from boto3_s3 import S3

S3().cp("local.txt", "s3://bucket/key")                       # zero config
S3(endpoint_url="https://minio.local:9000").ls(                 # MinIO
    "s3://bucket/", on_entry=lambda info: print(info.key)
)
S3(session=boto3.Session(profile_name="prod")).sync("s3://a", "s3://b")
```

| Member | Description |
|---|---|
| `S3(session=None, *, endpoint_url=None, config=None, transfer_config=None, reusable_after_interrupt=True, crt=None, filename_encoding=None)` | Holds the defaults: `session` (a `boto3.Session`; `None` selects a default session) plus `endpoint_url` / `config` (a `botocore.config.Config`) for building clients, and a default `TransferConfig` for `cp` / `mv` / `sync`. `reusable_after_interrupt` declares the app's Ctrl-C posture for every operation: `True` = a `KeyboardInterrupt` propagates only after full resource reclamation (the next operation stays callable); `False` = the app treats Ctrl-C as process-fatal, so the unwind may abandon a scan's in-flight listing page pull (the CLI's setting). It scopes to `KeyboardInterrupt` alone (`SystemExit` and every exception always reclaim fully) and the interrupt is re-raised, never converted - on the CRT engine too, whose manager would discard a drain-time interrupt ([`crt.md`](./crt.md) section 6). `crt` is the CRT engine's own client settings, a `CrtClientOptions` (lock posture, signing, TLS trust source; design/crt.md sections 4 and 6); every default keeps boto3's own behavior. `filename_encoding` is the POSIX file-name encoding of every `LocalStorage` that `resolve` builds (`None` = Python's file system encoding; an unknown codec raises `InvalidValueError`). All optional; `S3()` is the zero-config form. When the default session is created is an implementation detail. |
| `S3.from_aws_cli(*, profile=None, region=None, endpoint_url=None, no_verify_ssl=False, ca_bundle=None, no_sign_request=False, cli_read_timeout=None, cli_connect_timeout=None, cache_credentials=True, transfer_config=None, reusable_after_interrupt=True)` | An `S3` (of the class it is called on) whose session and clients are aws-cli's assembly (`boto3_s3.awsclisession.AwsCliAssembly`, built from the same `aws` common options in snake_case): aws-cli's profile and region chains, its bundled botocore's retries and us-east-1 regional endpoint, CRC64NVME as the default request checksum (stamped by its clients, named in an upload's transfer options by `_upload_options`), the CRT client's trust source and lockless posture (`CrtClientOptions`), aws-cli's local file-name encoding, and temporary credentials in `~/.aws/cli/cache`. The session opens at once, so profile / config / endpoint / CA failures raise there; a CRT run with no region resolved raises `ConfigurationError` before it starts (`_require_crt_region`). `client()` builds through the assembly. Nothing process-wide changes (`pin_proxy_connect` is the application's to call). design/overview.md section 3 has the boundary with `S3()`. |
| `session` | Read-only view of the constructor's `session` argument - the `boto3.Session` that supplies this instance's default clients and AWS config, or `None` for the zero-config form. |
| `reusable_after_interrupt` | Read-only view of the Ctrl-C posture declared at construction. |
| `client() -> S3Client` | The client factory (override seam). Builds a **fresh** boto3 S3 client from the instance's `session` / `endpoint_url` / `config`, **owned by the caller** - `S3` keeps no connection, hence no `close()`. Override to change credentials, memoize/reuse a client, or return a test double. |
| `resolve(loc) -> Storage` | The URL-interpretation seam (used by `cp` / `mv` / `sync`). A `Storage` instance is returned verbatim; an `"s3://..."` string becomes an `S3Storage` carrying `client()`; anything else is a `LocalStorage` with this instance's `filename_encoding` (aws-cli's rule: only `s3://` is special). Override to add schemes such as `http://`, deferring the rest to `super().resolve(loc)`. For the storages `resolve` itself produces, its inverse is `Storage.as_text()` - the canonical aws-cli path-shape token that `str(storage)` returns (a stream wrapper's `"-"` is display-only and does not round-trip). How a side enters a transfer plan is `Storage.format()`, which the planner (`transferplan`) consumes. |
| `aws_config() -> AwsConfig` | Reads this instance's AWS config file (`~/.aws/config`) through its session. The transfer operations read the profile's `[s3]` section through it (`resolve_transfer_config`); an application reads any other profile setting with it. Memoized per instance. See section 5. |
| `resolve_transfer_config(transfer_config=None, *, copy=False) -> TransferConfig` | The config a `cp` / `mv` / `sync` / `rm` run uses: each setting the caller gave in *transfer_config* (the instance's when `None`), else the profile's `[s3]` value, else `aws s3`'s default; the engine is picked as `aws s3` picks it, always classic for an S3-to-S3 *copy*. The operations call it themselves; an application calls it to hand one config to `materialize_crt_engine` and the run. Section 5. |
| `materialize_crt_engine(client, *, transfer_config=None)` | Builds the CRT transfer engine ahead of any transfer and drops it, for an application that wants the engine's construction failures to land where `aws s3`'s do (the CLI calls it at aws-cli's manager-construction slot, [`crt.md`](./crt.md) section 4); a classic selection makes it a no-op. |
| `cp` / `ls` / `mv` / `rm` / `mb` / `rb` / `presign` / `sync` / `website` | The operations, mirroring `aws s3 <sub>`. Where a `transfer_config` argument is accepted it defaults to the instance's `transfer_config` and is overridden per call; either way `cp` / `mv` / `sync` / `rm` fill the settings it leaves unset from `[s3]` (`resolve_transfer_config`). |

`ls` is a blocking push operation like the other batch methods: it delivers
`FileInfo` entries to its required `on_entry` callback and returns
only after listing and prefetch cleanup finish. It asks for no sort
(`ScanOptions.sort` stays `False`), so ordering is a property of the listing
it happens to run: a recursive object listing of a general-purpose bucket
arrives in S3's own byte order, but the non-recursive form emits each page's
common prefixes ahead of that page's objects, a directory bucket (S3 Express)
lists unordered, and a bucket listing promises no order either.
`ls` / `cp` / `mv` / `rm` /
`sync` accept a shared `CancelToken`; cancellation behavior is described in
[`exceptions.md`](./exceptions.md) section 3.

The `S3` instance's own state is thread-safe to share (immutable defaults plus
one benign, idempotent `aws_config()` cache), but its clients need care on two
counts: `client()` is **not safe to call concurrently** (it goes through boto3's
session, a not-thread-safe construction path), and boto3-s3 uses `s3transfer`
internally, whose per-transfer setup is **not thread-safe on a shared client**.
So to run operations in parallel across threads, **build one client per thread
sequentially, up front**, then give each thread its own via
`S3Storage(uri, client=...)` - never share a client, and never build clients
concurrently.

## 2. Resolution and client inheritance

A bare string argument inherits this `S3`'s client defaults; an explicitly
constructed `Storage` is used as-is.

| Argument | Resolves to |
|---|---|
| `"s3://bucket/key"` (`cp` / `mv` / `sync`) | `S3Storage` carrying `client()` |
| `"local/path"`, `"./x"` (`cp` / `mv` / `sync`) | `LocalStorage` |
| `"bucket/key"` or `"s3://..."` (the S3-only ops: `ls` / `rm` / `mb` / `rb` / `presign` / `website`) | `S3Storage` carrying `client()` - these ops are **lenient** about the `s3://` prefix |
| an `S3Storage(uri, client=...)` you pass in | used verbatim (its own client, **not** this `S3`'s) |
| an `IOStorage(stream)` / `StdioStorage()` you pass in (`cp`, or a non-recursive `mv` destination) | used verbatim - a stream side, transferred via its `open()` (the other side must be S3) |

Pass an explicit `S3Storage(uri, client=...)` when a single operation needs more
than one client - e.g. **S3-to-S3 across accounts** (a different client per
side), or a per-location endpoint. The instance default applies only to bare
strings.

An explicitly constructed `Storage` also carries its **source-config** - how that
source is read - which the operation honors: `LocalStorage(path,
follow_symlinks=…, detect_symlink_loops=…, enumerate_all_entries=…)` for the local walk,
`S3Storage(uri, page_size=…, fetch_owner=…)` for the S3 listing. A bare string
resolves to a storage with the defaults, so to tune the walk / listing, pass a
configured `Storage` rather than a per-operation argument (the knobs live on the
storage, seeded into every scan by `default_scan_options`; see
[`storage.md`](./storage.md)). This is how the CLI reproduces `--follow-symlinks`
/ `--page-size`: it bakes each flag into the storage it builds.

The strict `s3://`-vs-local split lives in `resolve`; the **CLI layer** narrows
the inputs to `aws s3`'s with the stricter per-subcommand `s3://`-required rules
on top - the library may accept more (see [`overview.md`](./overview.md)
section 3).

## 3. Module-level convenience functions

`boto3_s3.cp` / `ls` / `mv` / `rm` / `mb` / `rb` / `presign` / `sync` /
`website` are thin wrappers over a default `S3()`, for the common zero-config
case (`boto3_s3.sync(...)` instead of `S3().sync(...)`). Each keeps its method's
exact signature for type checkers and IDEs (a `ParamSpec` delegator, with the
method as the single source of truth). They build a fresh `S3()` per call - there
is no shared singleton; for configured behavior use `S3(session=...).sync(...)`.

## 4. Customization by subclassing

```python
class MyS3(S3):
    def client(self):                      # custom credentials / a mock in tests
        return my_session.client("s3", config=my_config)

    def resolve(self, loc):                # add an http:// backend
        if isinstance(loc, str) and loc.startswith("http://"):
            return HttpStorage(loc)
        return super().resolve(loc)
```

Overriding `client()` to memoize a client makes that subclass own a connection;
it then takes on the cleanup (a `with` / `close()` of its own). The base `S3`
deliberately keeps none, so it stays thread-safe and lifecycle-free.

The S3-only operations (`ls` / `rm` / `mb` / `rb` / `presign` / `website`) accept
only an `S3Storage` (a subclass customizing S3 behavior included), never an
arbitrary custom `Storage` - each needs an S3 bucket and client. A **stream**
Storage (`IOStorage` / `StdioStorage`) is transferable: `cp` reads / writes it
through its `open()` (one S3 side plus the stream), and a stream is also a
valid non-recursive `mv` *destination*. A custom *container* `Storage` (e.g. an
HTTP backend) transfers through the same `open()` route, again with one side
always S3 (`cp` / `mv` / `sync` only). The contract is in
[`storage.md`](./storage.md); the design is in [`transfer.md`](./transfer.md)
section 12.

## 5. Reading the AWS config file

`s3.aws_config()` exposes the AWS config file (`AWS_CONFIG_FILE`, default
`~/.aws/config`) as an `AwsConfig` reader. It is a **general** reader - not
limited to `[s3]` - that pulls any value the app did not set itself out of the
profile (or another section). The parse is delegated to botocore
(`Session.full_config` / `get_scoped_config`), so the file location, the nested
`s3 =` subsection syntax, and active-profile resolution match `aws` / `boto3`
exactly - including botocore's merge of the credentials file's profile values
into the map (a key set only in `~/.aws/credentials` is visible here, and on a
same-key collision the credentials file's value wins), just as `aws configure
get` sees them.

```python
cfg = s3.aws_config()
cfg.get_size("s3.multipart_chunksize", 8 * 1024**2)   # active profile, "16MB" -> bytes
cfg.get_str("region", None)
cfg.profile("prod").get_int("s3.max_concurrent_requests", 10)
cfg.services("my-svc").get_str("s3.endpoint_url", None)  # [services my-svc]
cfg.sso_session("my-sso").get_str("sso_region", None)  # [sso-session my-sso]
cfg.plugins().get_str("cli_legacy_plugin_path", None)
```

Mirroring `aws configure get`, the **profile is the default context** (the bare
getters read the session's active profile) and `services` / `sso_session` /
`plugins` are explicit selectors, each returning a `ConfigSection`. The two
deliberate additions over `aws`'s loader: **typed getters** (`get_str` /
`get_int` / `get_size` / `get_bool` / `get_rate`; sizes/rates are 1024-based to
match `aws s3`) and **caller-supplied defaults**. A missing key or absent named
section returns the default; a present-but-unconvertible number, or a key
naming a whole subsection, raises `InvalidConfigError` (`get_bool` is the one
exception: it keeps botocore's `ensure_boolean` semantics, where anything but
a case-insensitive `"true"` reads as `False`); a set-but-missing active
profile surfaces botocore's `ProfileNotFound` as an `InvalidConfigError`.
(`InvalidConfigError`'s parent is `ConfigurationError`, so a single
`except ConfigurationError` catches all of these.)

`AwsConfig` lives in `boto3_s3.awsconfig`, re-exported at the package root and
equally reachable by submodule path (`from boto3_s3.awsconfig import
AwsConfig`); importing it stays SDK-free.

**The `[s3]` section reaches the transfer operations by default**, as the
region reaches the client. `cp` / `mv` / `sync` / `rm` read the active
profile's `[s3]` through `aws_config()` at the start of each run and apply
`aws s3`'s semantics to it in `boto3_s3.transferconfig`, a port of aws-cli's
own `transferconfig.py`: the defaults table, the size / rate / boolean
spellings, validation (`InvalidConfigError`), the `default` -> `classic`
alias, and the classic / CRT engine decision ([`crt.md`](./crt.md) section 4).
Each setting comes from the first of: the caller's `TransferConfig` (a value
passed to its constructor; the library's `TransferConfig` records which ones
were), the `[s3]` section, `aws s3`'s default. A plain
`boto3.s3.transfer.TransferConfig` counts as the caller's in every value -
not every boto3 can tell its defaults apart - and is used as it is. There is
no switch to skip the file: like boto3, the library reads what the session's
config file says, and `AWS_CONFIG_FILE` (or the session's own `config_file`)
points it elsewhere.
