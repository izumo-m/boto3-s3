# The `S3` object

`S3` is the entry point for the `aws s3`-style operations. This page specifies
the object itself: its constructor (with the `CLIENT_REGION` / `CrtRegion`
names its CRT-region posture is spelled in), the `client` / `resolve` /
`aws_config` / `materialize_crt_engine` seams, and its thread-safety and
subclassing contracts. Each operation method
is specified on its own page under [`operations/`](./operations/README.md). The
narrative introduction is
[`../library/s3-object.md`](../library/s3-object.md); the rationale is
[`../../design/s3.md`](../../design/s3.md).

## S3

A stateless orchestrator. `S3` carries optional defaults — a boto3 session, an
endpoint, a botocore config, a transfer config, and the Ctrl-C posture — and
holds no connection of its own: there is no `close()` and nothing to release,
so a single instance can serve a whole application and be shared freely (the
one carve-out is a subclass whose `client()` memoizes; see
[Subclassing](#subclassing)). Every operation resolves its `Location`
arguments to [`Storage`](./storage.md#storage) objects and drives those: a bare
string inherits this instance's defaults, while a `Storage` instance passed in
is used verbatim, with its own client and its own scan configuration.

```python
S3(
    session: Session | None = None,
    *,
    endpoint_url: str | None = None,
    config: Config | None = None,
    transfer_config: TransferConfig | None = None,
    wait_on_interrupt: bool = True,
    crt_allow_absent_credentials: bool = False,
    crt_allow_lockless: bool = False,
    crt_region: CrtRegion = CLIENT_REGION,
)
```

`session` is the `boto3.Session` that [`client()`](#client) builds from and
that [`aws_config()`](#aws_config) reads through. `None` means clients come
from `boto3.client("s3")` — the process-wide default session, resolved exactly
as `boto3.client` itself resolves it. [`boto3_s3.session()`](./misc.md#session)
returns a drop-in `boto3.Session` whose clients parse response timestamps
through a C fast path, in place of the generic dateutil parse that dominates
the cost of large listings.

`endpoint_url` and `config` are applied to every client `client()` builds, for
an S3-compatible endpoint and for a `botocore.config.Config`. Neither reaches a
client that came in on a caller-constructed `Storage`.

`transfer_config` is the default [`TransferConfig`](./options.md#transferconfig)
for `cp` / `mv` / `sync`. Those methods take a `transfer_config=` argument of
their own; a value passed there replaces this default wholesale for that call,
and its own default of `None` selects this one. The annotation is boto3's
`boto3.s3.transfer.TransferConfig`; the library's `boto3_s3.TransferConfig`
subclasses it and adds the library-only settings.

`wait_on_interrupt` declares the application's Ctrl-C posture once, for the
operations this instance runs. `True` (the default) means a `KeyboardInterrupt`
propagates only after the operation has reclaimed its resources — every
enumeration worker it started is joined — so an application that catches the
interrupt can keep calling operations. `False` means the application treats
Ctrl-C as process-fatal: the unwind may abandon a scan's daemon prefetch worker
rather than wait out an in-flight listing page pull (the setting the `boto3-s3`
command uses). Either way the interrupt itself is re-raised, never converted or
swallowed — with one engine-imposed exception: pip s3transfer's CRT manager
discards an interrupt that lands in its transfer drain, so a CRT-engine run cut
short there raises [`BatchError`](./exceptions.md#batcherror) with the
cancelled items counted as failures instead; the classic engine re-raises even
there. The posture scopes to `KeyboardInterrupt` alone: `SystemExit` and
every other exception always get the full reclamation. It reaches the
operations that enumerate — `ls`, `rm`, and the non-stream routes of `cp` /
`mv` / `sync` — as [`ScanOptions.wait_on_interrupt`](./options.md#scanoptions)
on every scan they start; `mb` / `rb` / `website` issue a single call and
`presign` none at all, and none of them starts a worker, so there is nothing
for the posture to govern.

`crt_allow_absent_credentials` decides what the CRT transfer engine does when
the client resolves no credentials at all. `False` (the default) is boto3's
rule: the CRT engine is refused, the transfer runs on the classic engine, and
it fails with botocore's `Unable to locate credentials`. `True` is `aws s3`'s:
the CRT client is built around a credentials delegate that has nothing to
resolve, so the transfer is attempted and fails from inside it — which the
interpreter reports as an `Exception ignored in:` block followed by a
`AWS_AUTH_CREDENTIALS_PROVIDER_DELEGATE_FAILURE` result line. Set it only to
reproduce `aws s3`'s output; it is what the `boto3-s3` command sets. It has no
effect unless
[`TransferConfig.preferred_transfer_client`](./options.md#transferconfig)
selects the CRT engine, and it relaxes nothing else about which client may
share the process-wide CRT client.

`crt_allow_lockless` decides what an **explicit**
`preferred_transfer_client="crt"` does when another process of this
application already holds the cross-process CRT slot. `False` (the default) is
boto3's rule: the run silently selects the classic engine. `True` is
`aws s3`'s: the lock is acquired best-effort and the CRT client is built
regardless, so a construction-time failure (a bad CA bundle, an unresolved
region) surfaces under contention exactly as it does without it. An `"auto"`
preference respects the lock either way — that is `aws s3`'s own `auto`
resolution. Set it only to reproduce `aws s3`'s behavior; it is what the
`boto3-s3` command sets.

`crt_region` names where the CRT transfer engine takes its region from. Its
type is `CrtRegion` — a region string, `None`, or the sentinel `CLIENT_REGION`;
both names are importable from the package root, and `CLIENT_REGION` is the
default. `CLIENT_REGION` is boto3's source: the
built client's own resolved region. Any other value is the application's
already-resolved region and is used verbatim — `None` included, which declares
that no region resolved at all. The distinction only shows in that last case:
botocore hands a region-less client the `aws-global` pseudo-region, while
`aws s3` resolves its own region chain to `None` and awscrt then refuses to
build a client (its `assert isinstance(region, str)`, which the interpreter
reports as a bare `AssertionError` carrying no message). Set it only to
reproduce `aws s3`'s behavior; it is what the `boto3-s3` command sets. Like
`crt_allow_absent_credentials` it has no effect unless
[`TransferConfig.preferred_transfer_client`](./options.md#transferconfig)
selects the CRT engine, and the value it declares is also what the process-wide
CRT client is pinned to, so a later client declaring a different region falls
back to the classic engine.

`session` and `wait_on_interrupt` are readable back as read-only properties.
`session` returns what was passed, including `None` — reading it does not
materialize a default session. `endpoint_url`, `config` and `transfer_config`
are held privately and have no public accessor.

### Locations and clients

The transfer operations (`cp` / `mv` / `sync`) resolve each side through
[`resolve`](#resolveloc), so that method's rules decide what a bare string
means and which client it gets.

The S3-only operations (`ls` / `rm` / `mb` / `rb` / `presign` / `website`)
resolve their single `target` themselves and do not pass through `resolve`. An
[`S3Storage`](./storage.md#s3storage) — a subclass of it included — is used
verbatim; an `os.PathLike[str]` is expanded with `os.fspath`; a `str` becomes
an `S3Storage` carrying a client from [`client()`](#client). These operations
are lenient about the scheme: `"bucket/key"` and `"s3://bucket/key"` are the
same target, and the bare `"s3://"` service root is a valid `ls` target. A
non-s3 string is never a local fallback, and any other argument — a non-S3
`Storage`, which carries no `__fspath__` — raises
[`ValidationError`](./exceptions.md#validationerror). The resolved storage is
then validated before the operation uses it, which is where the strict
`aws s3` checks (unsupported ARN forms, a key without a bucket) raise
`ValidationError`.

Because resolution is per argument, an operation given two bare `"s3://..."`
strings calls `client()` twice and runs on two distinct clients. To make one
operation use a specific client — a second account for an S3-to-S3 copy, or a
per-location endpoint — pass an explicit `S3Storage(uri, client=...)` instead
of a string.

### client()

```python
def client(self) -> S3Client
```

Builds a boto3 S3 client from this instance's defaults and returns it. The
client is fresh on each call and owned by the caller: `S3` keeps no reference
to it and closes nothing. It is built from `session` when one was given, else
by `boto3.client("s3")`; `endpoint_url` and `config` are applied either way.

`resolve` calls it for each `"s3://..."` string it turns into an `S3Storage`,
and the S3-only operations call it for a string or `PathLike` target. To reuse
one client explicitly, build it once and pass it in:
`S3Storage(uri, client=s3.client())`.

This is one of the two override seams; see [Subclassing](#subclassing).

Raises — a failed build surfaces as a translated
[`Boto3S3Error`](./exceptions.md#boto3s3error), never the raw botocore
exception:

- [`ConfigurationError`](./exceptions.md#configurationerror) — credentials or
  region that do not resolve.
- [`InvalidConfigError`](./exceptions.md#invalidconfigerror) — configuration
  that is set but unusable: a missing `AWS_PROFILE`, partial credentials, or a
  malformed `endpoint_url` (which botocore rejects with a plain `ValueError`).
- Any other botocore build failure is mapped by the same translator, which
  leaves an error shape it does not classify at the `Boto3S3Error` base.

### resolve(loc)

```python
def resolve(self, loc: Location) -> Storage
```

Interprets one [`Location`](./storage.md#location) as a `Storage`. Used by
`cp` / `mv` / `sync` for each side; the S3-only operations do not call it.

A `Storage` instance is returned unchanged — an `S3Storage` with its own
client, an [`IOStorage`](./storage.md#iostorage) or
[`StdioStorage`](./storage.md#stdiostorage) stream side, or a custom backend.
Otherwise the argument is taken through `os.fspath`, and a string starting with
`s3://` becomes an `S3Storage` carrying a client from [`client()`](#client).
Everything else becomes a [`LocalStorage`](./storage.md#localstorage): only
`s3://` is special, which is the AWS CLI's rule. A schemeless `"bucket/key"` is
therefore a local relative path here, unlike in the S3-only operations.

Resolution constructs permissively and sends no S3 request; the operation
validates the storage it gets back. Building the `S3Storage` for an `s3://`
string does call [`client()`](#client), so `resolve` raises what that call
raises — [`ConfigurationError`](./exceptions.md#configurationerror),
[`InvalidConfigError`](./exceptions.md#invalidconfigerror), or the
[`Boto3S3Error`](./exceptions.md#boto3s3error) base — for credentials, a
region, or an `endpoint_url` that do not resolve. An argument outside
`Location` — neither a `Storage` nor something `os.fspath` accepts — raises
`TypeError` from `os.fspath`, which is a type violation rather than a reported
failure.

This is the second override seam; see [Subclassing](#subclassing).

### aws_config()

```python
def aws_config(self) -> AwsConfig
```

Returns a reader over the AWS config file (`AWS_CONFIG_FILE`, default
`~/.aws/config`) resolved for this instance's `session`. With `session=None`
the reader binds to `boto3.DEFAULT_SESSION` when the process already has one —
the session the zero-config `S3()`'s clients also use — and otherwise to a
plain `boto3.Session()`, which gives the same default / `AWS_PROFILE`
resolution without installing a global default as a side effect.

This is an explicit opt-in building block. The operations never read the config
file themselves, so none of them carries a hidden dependence on ambient `[s3]`
settings; credentials, region and profile still resolve through boto3's own
chain, which does read the file. Applying `aws s3`'s own interpretation of
`[s3]` — its defaults table, its validation, its engine choice — is the
`boto3-s3` command's job, not the library's.

The reader is memoized per instance, so the file is parsed once in the common
case. That cache is the instance's only mutable state and is benign: concurrent
first calls may each build a reader, and whichever is stored reads the same
file.

`AwsConfig` is exported from the `boto3_s3` root and from
`boto3_s3.awsconfig`. Its own API — the typed getters and the `profile` /
`services` / `sso_session` / `plugins` selectors — is
[`./misc.md#awsconfig`](./misc.md#awsconfig); the narrative is
[the guide](../library/s3-object.md#6-reading-the-aws-config-file) and the
rationale
[`../../design/s3.md`](../../design/s3.md#5-reading-the-aws-config-file).

Raises [`InvalidConfigError`](./exceptions.md#invalidconfigerror) when
`session` is `None` and building the default session fails, which is what a
set-but-missing `AWS_PROFILE` produces. Reading a value can raise the same
class for a value that will not convert.

### materialize_crt_engine(client, \*, transfer_config=None)

```python
def materialize_crt_engine(
    self, client: S3Client, *, transfer_config: TransferConfig | None = None
) -> None
```

Builds the CRT transfer engine ahead of any transfer, for an application that
owes `aws s3` parity on *where* the engine's construction failures land.
`aws s3 rm` builds its transfer manager before deciding anything about the run,
so a CRT configuration it cannot construct — [`crt_region`](#crtregion)
declaring no region, above all — fails the command rather than the deletes;
`rm` here deletes through `DeleteObject` and never uses the engine, so it calls
this to pay the same construction at the same point.

The engine is chosen from *transfer_config*, falling back to the instance's own
`transfer_config`, with the rule the transfer operations apply: a classic
selection — explicit, or `auto` on a host the CRT is not tuned for — makes this
a no-op. Nothing is returned, because the CRT client is process-wide: a later
transfer on a compatible client reuses whatever this built. Raises
[`ValidationError`](./exceptions.md#validationerror) for a config that sets
classic-only tuning under an explicit `crt`, the same rejection a transfer
would raise.

### Operations

Nine methods mirror the `aws s3` subcommands. Each has its own page:

- [`cp(src, dest, ...)`](./operations/cp.md) — copy bytes.
- [`mv(src, dest, ...)`](./operations/mv.md) — copy, then delete the source.
- [`sync(src, dest, ...)`](./operations/sync.md) — recursive create / update /
  delete against a destination.
- [`ls(target, ...)`](./operations/ls.md) — list objects, common prefixes, or
  buckets.
- [`rm(target, ...)`](./operations/rm.md) — delete objects.
- [`mb(target, ...)`](./operations/mb.md) — create a bucket.
- [`rb(target)`](./operations/rb.md) — delete an empty bucket.
- [`presign(target, ...)`](./operations/presign.md) — sign a URL, client-side.
- [`website(target, ...)`](./operations/website.md) — set the bucket website
  configuration.

What they share — the accepted path forms, dry runs, cancellation, the result
stream, and the partial-failure model — is specified in
[`operations/README.md`](./operations/README.md), which also covers the
module-level mirrors `boto3_s3.cp` / `ls` / `mv` / `rm` / `mb` / `rb` /
`presign` / `sync` / `website`: thin wrappers that run the same method on a
fresh zero-config `S3()`.

### Thread safety

The instance's own state is safe to share across threads: the constructor
defaults are never mutated, and the `aws_config()` cache is idempotent. Its
clients are what need care, on two counts. `client()` is not safe to call
concurrently, because it goes through boto3's session construction path.
`s3transfer`, which moves the bytes, is not thread-safe in its per-transfer
setup on a shared client.

So the supported way to run operations in parallel is to build one client per
thread sequentially, up front, and give each thread its own through
`S3Storage(uri, client=...)`: never share a client between concurrent
operations, and never build clients concurrently. Passing bare `"s3://..."`
strings to concurrent operations is exactly the unsupported case, since each
operation would build its own client at the same time as the others.

A callback is a separate contract: `on_result`, `on_progress`, and the
`filter` predicates of `cp` / `mv` / `rm` / `sync` may be invoked from worker
threads, and each operation's page states which. Keep them fast, non-raising,
and thread-safe.

### Subclassing

`client()` and `resolve()` are the supported override points.

```python
class MyS3(S3):
    def client(self):
        return my_session.client("s3", config=my_config)

    def resolve(self, loc):
        if isinstance(loc, str) and loc.startswith("http://"):
            return HttpStorage(loc)
        return super().resolve(loc)
```

Overriding `client()` changes credentials, session, or endpoint for everything
that does not carry its own client, and is also how a test double is
substituted. An override that memoizes makes the subclass own a connection, and
with it the cleanup the base class deliberately has none of.

Overriding `resolve()` adds URL schemes, deferring the rest to
`super().resolve(loc)`. Its reach is the transfer operations alone: `ls` / `rm`
/ `mb` / `rb` / `presign` / `website` bypass it and always read their target as
S3, so their endpoint and credentials are customized through `client()` only.

What can be substituted has limits. Where a `Storage` is passed, the S3-only
operations accept only an `S3Storage` — a subclass of it included — never an
arbitrary custom `Storage`, since each needs an S3 client and reads its target
as S3 (`ls` alone also accepts the bucketless service root). A custom
`Storage` participates as one side of a `cp` / `mv` / `sync` transfer, with the
other side always S3; the capability requirements for that route, and for a
stream side, are in [`storage.md`](./storage.md).
